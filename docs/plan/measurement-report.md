## Methodology

Source: opencode 1.19.0 SQLite store `~/.local/share/opencode/opencode.db`
(tables `session` / `message` / `part`; `part.data` JSON). Large tool outputs are
offloaded to `~/.local/share/opencode/tool-output/<callID>`; the miner takes
`max(inline state.output bytes, offload file bytes)` per tool part.

Unit of "provider request" = one assistant message (one model turn). Parts are
ordered by `part.time_created` within a session; turns by `message.time_created`.

Definitions (constants mirror SoL-Pi: `THRESHOLD_BYTES=10240`, 2 full sends kept,
4 chars/token):

- **Action Fusion adjacency** — an `edit|write|patch|multiedit` tool part whose
  *next* tool part is a `bash|shell|run|exec` part in the **same turn** or in the
  **immediately following assistant turn**. Rate = adjacent / all edit parts.
- **Eligible cross-turn transitions** (SoL-Pi-comparable 12.3% figure) — of all
  consecutive tool-bearing assistant turn pairs, those where the previous turn's
  *last* tool is edit/write and the next turn's *first* tool is a run.
- **Bash share of next-actions** — among next-actions taken after an edit/write
  part, share that is `bash` (SoL-Pi reference: 85.1%).
- **ObservationPack replay** — for each tool output ≥ 10 240 B first appearing in
  turn *i* of a session with *A* assistant turns:
  `replays = max(0, (A − i − 1) − 2)`, `replayableBytes = size × replays`,
  `tokens = bytes / 4`. This is the upper bound ObservationPack could remove.
- **OCC compaction activity** — count of `compaction`-typed parts plus
  `session.time_compacting IS NOT NULL`.

### Reading of the baseline

- **Action Fusion: headroom present but shaped differently.** 26.4% of edit parts
  are already followed immediately by a run, and 10.2% of cross-turn transitions
  are eligible — close to SoL-Pi's 12.3%. But bash is only 26.6% of the
  next-actions after edits (vs 85.1%): these sessions interleave edits with
  read/grep/webfetch rather than edit→test loops, so the *fusion* opportunity is
  real but narrower than the reference; the adjacency rate is dominated by
  same-turn edit→bash pairs that fusion could collapse into one call.
- **ObservationPack: largest quantified headroom.** ~1.95 M replay tokens
  (11.1% of billed tokens) sit above the 10 KiB threshold and beyond the 2 kept
  sends — same order as SoL-Pi's −23.58% bill claim, though that figure is a
  *bill* delta on coding workloads and this is a token upper bound on
  orchestration workloads. Concentration is high: one session (jolly-mountain)
  holds 827 k of it; the single largest output contributes 219 k tokens.
- **OCC: zero headroom in this dataset.** No compaction ever fired
  (`time_compacting` NULL in all 16 sessions, no compaction parts). Either the
  sessions stayed under the compaction trigger or compaction is not exercised by
  this workload — OCC cannot be validated from these logs at all.

### Caveats (explicit)

1. **These are orchestration sessions, not coding workloads.** They are this
   repo's own P0–P5 build sessions (agents driving read/edit/bash loops with no
   compile/test cycle). SoL-Pi's numbers come from EdgeBench coding tasks; the
   edit→test adjacency that Action Fusion targets is structurally under-represented
   here, and no build/test failures are replayed.
2. **Small n / single window / single provider** (`devbox-ai` proxy, `cost = 0`) →
   token-only, no bill comparison; no paired runs yet; ±noise unquantified.
3. Replay estimate is an **upper bound**: it assumes every post-second appearance
   of a ≥10 KiB output is re-sent verbatim and that ObservationPack would have
   archived it; it ignores cache-read pricing differences and any content that
   was actually re-derived.
4. The DB is live: the run includes the sessions created by this measurement work.
   Re-run the command above to refresh; `measurement-baseline.json` is the
   machine-readable snapshot of the numbers quoted here.
